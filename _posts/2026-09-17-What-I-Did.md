本文是 RoughAgent 的实现说明，分四部分：上下文治理、成本审计、测试与评测、权限与审批。每部分按同一顺序展开：做了什么、为什么这样做、结果如何。

数据来源是会话日志的成本审计、测试报告与扩展自带的统计。未做实测的部分会标注为读文档得出或上界估计。

## 一、上下文治理

### 成本结构

7 个会话、1,283 次请求的审计结果：

| 项 | token | 单价 | 金额 | 占比 |
|---|---|---|---|---|
| 缓存读 | 441,347,200 | ¥0.02/M | **¥8.83** | 53% |
| 输出 | 1,507,138 | ¥4/M | ¥6.03 | 36% |
| 未命中输入 | 1,550,800 | ¥1/M | ¥1.54 | 9% |

缓存读单价为未命中输入的 1/50，但量是 293 倍，因此它是最大的一笔支出。未命中输入仅占 9%，缓存机制本身有效。

成本公式为：

```text
总缓存读 = Σ(每次请求时的上下文大小) × ¥0.02/M
```

该式决定了优化目标是降低每次请求时的上下文大小，而不是减少对话轮数。

![前缀构成：工具调用参数 44~54%、思考 32~37%、工具返回 11~14%](context/prefix-anatomy.webp)
_按字符统计的全部消息内容占比_

前缀构成为：工具调用参数 44~54%，思考 32~37%，工具返回 11~14%，模型正文 3~4%，用户输入 0.2%。工具参数中单个 `write` 占 56.7%（196 次调用，871,876 字符），这部分文件内容已落盘，需要时可重新读取。

### 增长曲线

09-17 会话（625 次请求）的上下文占用：

```text
#1=3K   #5=9K    #100=181K  #200=327K
#300=439K  #400=556K  #500=693K  #600=817K

每轮增加约 1.3K token，峰值 844,221，全程未触发压制机制。
```

近似线性增长。结合成本公式，上下文线性增长意味着总成本随会话长度呈平方级增长；两个长会话占总成本的 89%。

### 两条压缩路径

内核自带压缩（compaction）：上下文接近窗口上限时，将较早历史摘要为一条消息并替换。该方式是一次性的大幅替换，摘要本身产生输出费用。

在其之上增加了治理扩展 `rough-context-curator`：挂在内核的 `context` 事件上，在每次 provider 请求前改写 messages，对历史消息中超阈值的工具结果做保留头尾的截断。默认档位：

```text
单条超过 8000 字符 → 保留头部 1500 + 尾部 600 + 截断标记
```

三项实现约束：

- 最新一轮不处理，避免影响当前推理；
- 只处理 content 型消息（text 块），不修改结构化字段；
- 不注册任何工具，因此没有固定 token 开销。

![压缩与治理的差别](context/curate-vs-compact.webp)
_压缩为一次性替换，治理为每轮小幅截断_

### 档位在会话内冻结

档位可配置（`settings.json` 的 `roughCurator` 段），生效时机不是立即：每个会话在第一次真正发出请求时读取一次，之后冻结。已开始的会话继续使用旧档位，新会话使用新档位。

原因与缓存有关：截断结果决定缓存前缀。若在会话中途将阈值从 8000 调到 20000，被截断的内容会重新出现在前缀中，从该条消息起前缀失配，其后每次请求均按未命中计价。

![档位冻结的生效方式](context/freeze.webp)
_同一次改动：已开始的会话不变，新会话生效_

### 两个未启用的池

治理可覆盖但默认关闭的两项：

| 项 | 占前缀 | 说明 |
|---|---|---|
| 工具调用参数 `toolArgs` | 44~54% | 已定位的最大浪费，约 ¥2.64，占总额 16% |
| 思考块 `thinking` | 32~37% | 与工具参数同一量级 |

两者默认关闭的原因相同：它们修改的是模型自身的输出（文件内容、推理链），模型需要回看这些内容维持上下文连续性，改成摘要后的效果未经实测。机制已实现、可配置、可关闭，默认不开启，待 A/B 验证后再定默认值。

协议层面的一条约束：DeepSeek 在请求带 `tools` 时要求回传历史轮次的 `reasoning_content`，缺失会返回 400。要求的是字段存在，不要求内容逐字一致。

### 效果统计

治理以纯钩子方式运行。若不加统计，外部只能观察到上下文增长变慢，无法验证。因此增加了 `context-report`，输出三项：

1. 按请求累计少发的字符数，以及 token 估算值；
2. 压缩前的上下文占用。`lastContextUsed` 表示当前值，压缩发生后会被改写，因此需要冻结压缩前的最后一次观测；
3. 会话内上下文占用峰值。与第 2 项不同，峰值在压缩后仍会继续增长。

![数据面板中的上下文治理区域](context/panel-context.webp)
_生效档位、峰值占用、压缩前占用、可省未省_

该层的四条约束：

- 只观测，不做决策。开关与阈值仍由插件开关和 `settings.json` 决定；
- 字符数不折算为金额。省下的输入有一部分本就命中缓存（单价为未命中的 1/50），折算会高估收益；
- 观测点与真实值同源，只在 `lastContextUsed` 更新时记录，不另设采样定时器，避免面板数值与 usage 不一致；
- 无数据时不显示，不输出“省了 0 字符”这类无意义行。

报告包含 `uncovered` 字段，表示“可治理但开关关闭”的两块内容大小。该字段为 0 有两种情况：开关已开启，或历史中确实没有超阈值内容。界面需要区分这两种情况。

### 压缩的两条触发路径

阈值路径：内核判据为 `contextTokens > contextWindow - reserveTokens`。`reserveTokens` 默认值为 16,384，当前模型档案的 `contextWindow` 为 1,000,000，因此触发点为 983,616，实测峰值 844,221 从未达到。

溢出路径：另一条判据为 `stopReason === "length" && usage.output < model.maxTokens`，不经过上述阈值。当前 `maxTokens` 为 8192，实测输出停在 8190/8192。该判据在数个 token 的范围内即可翻转，翻转后的行为是反复压缩整个上下文。

因此压缩配置层不只暴露阈值，同时报告溢出路径的风险。缺省值需与内核 `SettingsManager.getCompactionSettings()` 一致，由单元测试直接调用内核接口固定，避免内核升级后界面显示值与实际生效值不一致。

## 二、成本审计

### 方法与总量

数据源为 `~/.rough-agent/sessions-pi/*.jsonl` 下的 7 个会话、1,283 次请求，全程只读。单价取自 `balance.ts` 的单价表（deepseek-flash 空闲价：未命中 ¥1/M、命中 ¥0.02/M、输出 ¥4/M），与官方定价页一致；峰谷按工作日 9–12 / 14–18 高峰翻倍，周末与法定节假日全天低谷。

统计结果 ¥16.78（未计峰谷为 ¥16.40，差额来自高峰时段的 43 次请求）。

### 三个被定位的浪费

**write 参数的历史驻留。** 每个 `write` 调用产生的 `content`，会在此后每一次请求中被重读。

| 会话 | 请求数 | write 参数字符 | 被重读总量 | 折合成本 |
|---|---|---|---|---|
| 09-17 | 625 | 701,996 | 223,168,790 字符 | **¥2.23** |
| 09-20 | 453 | 142,502 | 40,934,394 字符 | ¥0.41 |
| 其余 | 205 | 27,378 | 318,628 字符 | ~¥0 |
| 合计 | | | | **¥2.64** |

合计占总额 16%。09-17 会话中，这部分占其自身成本的 25%。这些内容已落盘，后续需要时可由模型重新读取。

**压缩从未触发。** 触发点为 `contextWindow − reserveTokens = 1,000,000 − 16,384 = 983,616`，实测峰值 844,221，7 个会话压缩 0 次。窗口配置为 1,000,000 与官方规格一致，问题在于内核默认余量 16,384 对 1M 窗口已不适用。

**治理对象错位。** 治理扩展按 8,000 字符阈值截断工具返回内容，而实测的 1,284 条工具返回中，中位数 86 字符、P90 为 902 字符、超过 8,000 字符阈值的仅 11 条。该部分只占前缀 11~14%；占 44~54% 的工具调用参数没有治理。

### 可用杠杆

![各杠杆的收益量级](cost/levers.webp)
_按收益排序，最后两项为排除项_

| 杠杆 | 收益 | 代价 | 状态 |
|---|---|---|---|
| 长任务勤开新会话 | 上界 82% | 重新交代背景 | 零代码，未实施 |
| 调早压缩阈值 | 约 25% | 细节被摘要 | 纯配置 |
| 裁剪历史 `write` 参数 | 约 16% | 需开发 + A/B | 计划中 |
| 治理面扩到工具参数 | 与上一条重叠 | — | 计划中 |
| 挪到低谷时段 | 2.3% | — | 已实施 |
| 降低思考档位 | ≈ 0 | — | 排除（已是低档） |

第一条的数据：同一个任务量拆成 100 次请求的短会话后，09-17 ¥5.65 → ¥0.88（84%），09-20 ¥2.92 → ¥0.50（83%），09-16 ¥0.26 → ¥0.17（37%），合计 ¥8.86 → ¥1.57（82%）。这是上界估计：新会话需要重新交代背景、重新读文件，实际收益会低于该值。其原理是成本为上下文大小的函数，而上下文只增不减，第 600 轮需要为前 599 轮的全部内容付费。

### 一条不可用的路径

思考占前缀 32~37%，按体量应是最优的优化点。用本地假端点检查第二轮请求体，确认历史思考确实被回传；查官方文档后确认该路径不可用：

| 场景 | 规定 |
|---|---|
| 带 `tools` 的请求 | 历史轮次的 `reasoning_content` 必须回传，漏传返回 400 |
| 不带 tools | 无需回传，传了也会被忽略 |

RoughAgent 属于带 tools 的情况，因此“剥离历史思考”不可用。

该结论来自读文档，未做实测验证。若要实施这条优化，第一步应是用一次真实请求确认漏传确实返回 400，单次成本低于一分钱，可避免整个前提错误。

### 计价层的四个实现点

**金额落盘，不实时计算。** 原实现中，`todayCost` 与轮次视图的金额在读取时用当前单价表乘以已存 token 现算，单价表变更会导致历史金额被重算。现改为在记账时按当时单价计算一次，并以整数存进 `usage.jsonl`。整数是配套要求：浮点值落盘后读回，减法比较会产生 `0.30000000000000004` 一类残差。精度取到微元（1e-6 元），单笔舍入误差不超过 0.5 微元，上万笔累计低于 1e-3 元。

**单价表曾出现低估。** 上一版把输出单价写为 2.0，为实际值的一半，而输出是三项中单价最高的一项，导致面板金额低于实际（实测一条会话：显示 ¥0.347，实际 ¥0.503，高峰时段差额更大）。

**未命中输入为反推值。** 缓存字段的映射为 `input + cacheRead` 记为总输入，未命中由差值反推。该口径写在字段注释中，避免被后续维护者当作原始字段。

**时间基准先转换时区。** 峰谷判断需要先转换到北京时间再取字段，否则宿主时区变更会导致高峰与低谷判定反转。峰谷规则附 2026 年节假日表。

单价属于会过期的外部事实：Flash 自 2026 年 4 月发布以来已调价三次（8/17 涨价并引入峰谷，9/10 回调），因此只保留一处事实源，并由单元测试直接固定。

### 一次结论纠正

内部评审初版写过“项目唯一的『花钱提醒』是那句 toast”。该结论有误：当时只查看了 `lib.ts` 就给出了全局判断。项目实际已有预算告警，位于数据面板的「预算告警」区域。

### 本次审计未覆盖的部分

- 单价与真实账单未做对账，没有可对照的官方月度账单；
- “能省多少”均为上界估计，未做 A/B；
- 因此本报告能回答“钱花在哪”，不能回答“能省到什么程度”。

### 三条纪律

1. 只读。审计过程不修改数据；
2. 口径写在字段注释里。字符不等于 token，token 不等于金额；
3. 结论标注性质：区分实测、上界估计、读文档得出。

## 三、测试与评测

### 三层分工

当前仓库有 151 个测试文件（后端 91、前端 60），另有一套 eval 任务集。三层回答不同的问题：

![三层防线](verify/three-layers.webp)
_单元测试、集成测试、eval 的分工_

| 层 | 回答的问题 | 方式 |
|---|---|---|
| 单元测试 | 零件是否正确 | 翻译表、审批策略、预算算法、PNG 编解码；全部 mock，零成本 |
| 集成测试 | 循环是否闭环 | Pi 循环 + 翻译层 + 审批 + 断言的整条链路；mock 全链路；内核升级后必跑 |
| eval | Agent 是否合格 | 任务成功率、平均步数、平均 token、失败模式分类；真实模型 + 确定性终态断言 |

贯穿三层的一条约束：断言只依赖确定性终态（文件内容、事件序列、工具调用集合），不匹配具体文案。模型换一种说法就变红的用例无法长期使用。

### 本地假模型服务

mock 服务按用户输入匹配剧本（`write`、`read`、默认三类），并维护状态机：新回合重选剧本、逐步推进到完成、工具调用 ID 连续计数。

作用是让回归测试零成本。同时它测的是 RoughAgent 自己这一层（翻译、审批、上下文治理、落盘），这部分在模型换代时不应变化。

### 基线门禁

最初的 runner 只判断“本次有没有任务失败”，能拦住变红，拦不住指标劣化：

```text
2 步完成的任务变成 5 步
token 从 7.5k 涨到 20k
成功率仍为 6/6，门禁放行
```

加入基线后，判定分两类：

- **回归**：同一任务上次通过、本次失败。属于确定的事实，两种模式下都阻塞合入；
- **指标劣化**：都通过但步数/token 超过阈值。属于度量，是否阻塞取决于模式。

![门禁的判定规则](verify/verdict-gate.webp)
_回归与指标劣化的不同处理_

分模式的原因：mock 模式剧本固定，token 与步数是确定值，指标上升即为真实上升；真实模型模式下，同一任务两次运行的 token 差异可达一两成（采样、缓存命中、供应商侧波动），若作为硬门禁会产生随机变红的 CI，进而导致所有告警被忽略。

### eval 任务集

任务按维度分组：`single-step`、`multi-step`、`self-heal`、`variant`、`search`、`discipline`、`precision`。每个任务包含独立工作区、可选的工作区预置、以及机器断言（抛错即失败）。

指标包含成功率、平均步数、平均 token，以及失败模式分类：

```text
turn-error      回合异常（LLM / 网络错误，非模型能力问题）
assert-failed   终态断言失败（模型未完成任务）
no-tool-call    未调用工具即结束（模型未理解任务）
```

失败分类的作用大于成功率：三类失败对应不同的处理方式——检查供应商状态、修改 prompt 或工具描述、修改任务表述。

最近一次 mock 报告：6 个任务全部通过，平均 2.33 步、8.8k token、111 毫秒。该结果说明护栏链路通畅，不代表模型能力；mock 模式下模型是假的。

因此 eval 采用双模式：mock 模式验证护栏（零 token），真实模型模式跑全量（发布判据）。

### 断言的两类失效

一类是“算出来又丢掉”：值已经计算，但没有任何出口。这类问题不会让任何测试变红。当前已固定三处：

1. **重试原因被替换。** 内核给出了原始错误（`429 Too Many Requests`、`401`、DNS 不通），实现的文案统一显示“服务商暂时不可用”，用户会倾向等待或重试，而不是更换密钥或修改配置；
2. **子代理上限只存在于代码里。** 界面文案手抄了一份数字，常量变更后文案不跟随，界面长期显示不成立的数值；
3. **插件生效时机的说明未在前端显示。** 开关只对新建会话生效，该说明必须出现在界面上。

另一类是断言本身失效。第 3 条最初写成源码扫描：断言某组件源码中出现该字段名。反向验证表明该断言无效——把 `if (d.note)` 改为 `if (false && d.note)`，扫描仍然通过。现已改为前端行为测试：渲染、点击开关、断言该说明出现在 DOM 中。

### 五条事故记录

**`atomic-write`：一次偶发的门禁红。** 全量测试中出现一次 `EPERM: rename '…/session-index.json.tmp' -> '…/session-index.json'`，重跑即通过。排查发现：记忆存储的注释已记录过该现象（临时文件被索引器或杀软短暂占用），并且只有该处实现了重试；另外 8 处手写的“写临时文件后改名”均未处理。这 9 处写入的对象均为用户数据：会话索引、模型档案与 apiKey、插件配置、用量台账、检查点、长期记忆。瞬态失败在测试中可以重跑，在用户侧表现为功能静默回退。

验证方式为注入失败：替换 `fs.renameSync` 为会失败的替身。瞬态问题无法通过反复运行验证。

**预算护栏的接线未被测试。** 纯函数与读写测试通过，但移除“强制停掉超预算会话”的代码后，这些用例仍然全部通过。该形态是“测了两端，漏了中间”。现改为走真实服务、真实 HTTP 端点、真实计价，断言会话确实被停止，而不只是发出了告警事件。

**假绿。** 上述用例的第一版虽然运行通过，但未验证任何内容：mock 模式下模型标签被强制写成 `mock`，而计价按标签匹配 DeepSeek，导致金额恒为 0，护栏不会触发。同组中“非 DeepSeek 不触发”的断言也因此恒为通过，与“用例根本没有执行”无法区分。

**`abort-during-retry`：中止后可停止，但前端收不到终止事件。** 服务商返回 503，界面显示“正在自动重试：第 1 / 3 次，2 秒后重试”，用户点击停止后服务端确实停止（provider 只被请求一次），但没有任何终止事件发出：输入框持续显示“生成中”，无法发送新消息，停止键无效。只有刷新界面才能恢复。根因是重试退避被中止时，内核发出的是 `agent_settled` 而非 `agent_end`，而翻译层当时只识别后者。

**`sse-resume`：断线续传的锚点。** 流式事件的续传最初使用毫秒时间戳作为锚点，存在两个问题：同一毫秒内的两条事件（文本事件与紧随其后的结束事件，mock 模式下更容易出现）会被“严格大于”的判定过滤掉一条，且不报错；时间戳缺失时回落为 0，导致整环 500 条事件全部重投，而前端未做去重，界面出现重复的整段对话。现改为自增的全局单调序号。

### 五条约束

1. 断言只依赖确定性终态，不匹配具体文案；
2. 涉及数字的文案由常量生成，单元测试直接比较常量；
3. 会随机变红的门禁降级为“只报告”；
4. 涉及外部事实的缺省值（内核默认值、单价表）与来源逐字一致，并由单元测试调用来源固定；
5. 源码扫描仅作辅助，行为测试作为门禁。

## 四、权限与审批

### 前提

Pi 没有内置权限系统：工具与扩展以 Pi 进程的操作系统权限运行，项目信任只决定加载哪些项目资源，不提供沙箱。因此权限层由 RoughAgent 实现。

### 四档权限

![四档权限](approval/ladder.webp)
_auto、confirm-writes、manual、plan_

| 档位 | 放行范围 |
|---|---|
| `auto` | 全部放行 |
| `confirm-writes` | 只读工具免审批（`read` / `grep` / `find` / `ls`），写操作进入审批 |
| `manual` | 全部工具进入审批 |
| `plan` | 先看计划：只读照常，写操作拦截至提交的计划获批 |

`manual` 档的实测数据：该档下 94.6% 的调用属于变更类。逐个确认会退化为无意义的点击，因此增加了“本会话内全部不再询问”一档，用于保证严格档位可用。

权限档位的类型定义放在 wire 契约（`protocol.ts`）中。三个取值曾分别在两处定义，增加取值或改名时会发生漂移。

### 默认拒绝

![审批流程](approval/fail-closed.webp)
_工具调用到放行的判定链_

三种情况直接拒绝执行：

- 审批通道未建立（桥未挂上）→ 拒绝；
- 120 秒内没有决议 → 自动拒绝。用户离开或界面卡死均按此处理；
- 一个回合收尾时仍未批准 → 统一拒绝。不将未完成的批准带入下一轮。

超时判定与回合收尾判定位于注入的决议方（审批桥），策略模块只负责判定与拦截。两者分离后，同一份策略可同时用于 Web、桌面端与终端。

### 硬禁止层

除四档权限外，另有一层硬禁止：判据是“该操作是否存在正当用途”，覆盖私钥目录与明文存放 apiKey 的 agentDir。该层与权限档位无关，任何档位、任何批准均不放行。

硬禁止层不挂开关。项目原则是“所有附加功能都关得掉”，而该层原先寄生在审批门内部，由门调用；一旦审批门按原则做成可关闭，关闭审批门会同时关闭该层保护，且不报错、界面无提示，私钥与 `models.json` 将可被任意读写。子代理路径此前已单独注入该层，现已统一。

对应三条测试：

1. 审批门可关闭；
2. 硬禁止层不经过任何开关（源码扫描：注入点的首标识符不是 `*On`）；
3. 关闭审批门后，硬禁止层仍然拦截（端到端真实会话）。

### 路径判定

`confirm-writes` 档“只读工具免审批”隐含一个前提：只读工具无法读取工作目录之外的内容。该前提不成立：Pi 的 `read` / `grep` / `find` / `ls` 接受绝对路径，且不做 cwd 钳制。

原实现只判断 `path.isAbsolute`，并在注释中说明“相对路径由 Pi 解析到 cwd 内，安全”。核查内核源码后确认：`resolvePath` 对相对路径使用 `path.resolve(baseDir, p)`，无 cwd 钳制；`normalizePath` 默认展开 `~`。因此在只读免审批档下，以下两条调用不会触发审批：

```text
read({ path: "../../../../Users/Admin/.rough-agent/models.json" })
read({ path: "~/.ssh/id_rsa" })
```

修法为先归一化再比较（`resolve` 并展开 `~`），Windows 下按大小写不敏感比较（文件系统不区分大小写，大小写敏感的 `startsWith` 可被绕过）。判错方向为多要求一次审批。

另一项取舍是哪些工具参与路径判定。仅 `write` 与 `edit`：它们的参数包含完整目标路径，判定为纯词法比较。`bash` / `powershell` 的实际改动无法从参数枚举，纳入判定会误伤正常流程（例如写临时文件）；这类工具只能依靠操作系统级沙箱。

### 两处实现的同步

同一份策略存在于两处：Web 与桌面端走 SSE 审批请求加 HTTP 决议；终端走 Pi 的确认框。同步方式为契约测试：同一组用例运行两份实现，只改一处会导致失败。

两处的已知差异写在代码注释中，避免被当作漏实现补齐：终端只有是与否两个选项，因此没有“本会话内全部允许”，也没有计划档。

其中一条处理规则：终端收到 `plan` 档时必须退到更严的 `confirm-writes`，不回落 `auto`。回落 `auto` 会把最严格的档位变成最宽松的档位，且不报错、无提示。

另一条：无法获取工作目录时不做猜测。猜错方向只是多弹一次确认框，但无依据的确认框会干扰正常流程。

### 四条约束

1. 每一步默认拒绝；
2. 底线不挂开关，可关闭的功能必须可关闭，并在界面说明后果；
3. 判错方向偏向更严：多一次点击优于多一次越权；
4. 安全层需要测试，且测试必须可证伪。“关闭审批门后底线仍然有效”这类断言必须端到端运行真实会话，仅做源码扫描的断言容易失效。
