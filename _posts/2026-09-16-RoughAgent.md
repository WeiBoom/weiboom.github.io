最开始要解决的问题是成本。每天用 AI 写代码，每次对话结束后界面上只有一行「本次消耗 12k tokens」，没有明细。

这 12k 里有多少是新内容、有多少是重复付费，是模型思考慢还是工具卡住，这一轮花了三分钱还是三毛钱，都看不到。

所以 RoughAgent 最早的两条要求是：**知道自己花了什么，用更少的消耗做更多的事。**

后来这两条要求写进了开发准则。

这类系统有一个通用名称：**Harness**，指模型之外的执行层——循环控制、工具调用、权限判定、上下文组装、成本统计均由这一层完成。RoughAgent 就是一层 Harness。

本文说明这两条要求如何落到架构与界面上。

## 一、成本控制

### 前缀缓存按字节匹配

降低 token 消耗的重点不在减少措辞，而在前缀缓存。

DeepSeek 这类模型的前缀缓存按**字节**匹配：同一会话中，若本次请求的前缀与上次逐字节相同，该段按折扣价计算；只要前缀变化**一个字节**，整段按未命中计价。

常见的中断缓存的做法：

- system prompt 里加入当前时间戳；
- 把所有技能描述写入提示词，包括与当前任务无关的部分；
- 工具列表随会话开关变化；
- 修改权限档位时同步修改 prompt。

以上做法都会中断前缀缓存。

### 两条规则：缓存锚与前缀瘦身

第一条是**缓存锚纪律**：凡是要进入请求前缀的内容，都必须恒定。

- 系统提示词中不出现时间戳、随机 id、“现在是第 N 轮”这类动态拼接；
- 插件开关只对新建会话生效，不在会话中途增减工具；
- 切换权限档位不写入 prompt。

第二条是**前缀瘦身**。Pi 内核会将跨 Agent 的技能目录无条件拼进提示词；宿主机上与本项目无关的技能合计一万多字符。关闭后的对比如下：

| 项 | 关闭前 | 关闭后 | 变化 |
|---|---|---|---|
| 稳定前缀 | 9,611 tokens | 5,252 tokens | −45% |

第三条关于**截断**：大工具结果滑出上下文窗口时会被截断。截断必须具有确定性：同一条消息始终截出同一形状。第一次截断会中断一次缓存，此后形状稳定，可重新命中，长会话整体收益为正。

该权衡写在代码注释中，避免被后续维护者当作缓存 bug 处理。

### 实测结果

| 指标 | 数值 |
|---|---|
| 样本 | 49 轮真实对话 |
| 稳态缓存命中率 | 87.2% |
| 命中率超过 90% 的轮次 | 一半以上 |
| 缓存累计节省费用 | 67% |
| 应付 / 实付 | ¥1.92 / ¥0.63 |

每一轮的用量增量都会落盘为 JSONL，任何优化都需要给出前后对比数据。

## 二、成本可视化

成本控制与成本透明是同一件事的两面：账目不透明，就无法判断优化是否有效。

### 实时记账

账单不能只在整轮结束后更新。长任务运行一小时，若金额只更新一次，无法判断任务卡在哪一步。

RoughAgent 在运行过程中持续更新金额。消息发出后即显示实时卡片；每次模型请求与响应都会更新金额、上下文占用与请求计数，并显示当前请求序号与已耗时（超过 30 秒标黄，超过 120 秒标红）。

执行中的工具带读秒（`grep … 5.0s`），可直接看出任务卡在哪一步。

### 行为路径

一轮结束后列出该轮的全部步骤：

```
文本 1.4s → read 137ms → read 132ms → read 1ms
→ write 2ms → open_file 1ms
```

| 指标 | 数值 |
|---|---|
| 工具调用 | 3 个 |
| 本轮总耗时 | 6.8s |
| 其中模型耗时 | 2.0s |
| 平均输出速率 | 225 tok/s |

据此可区分该轮的耗时来自模型还是工具，并可对比更换模型或调整思考档位后的差异。

![数据总览·轮次面板：单轮的输入/缓存读/输出堆叠、命中率与耗时](round-metrics.webp)
_数据总览·轮次：单轮的输入／缓存读／输出堆叠，加上命中率、请求次数与耗时_

### 一个已修正的口径错误

命中率的口径曾经错误：命中量在分母中被计入两次，导致结果低于真实值。该错误已修正。

### 子代理与预算线

**子代理**：主 Agent 委托出去的子任务同样消耗 token。子代理运行时，每次子请求结算都会实时入账。

另有两条预算相关机制：按近期增速预估“约 N 轮后触发压缩”；会话或每日预算线，超出时提示。

界面同时显示当前执行状态与实时花费。

## 三、五条工程准则

以下五条为硬性约束。

### 不修改内核源码

Agent 的循环、工具执行、上下文压缩运行在 Pi 内核上，版本精确锁定；所有定制通过内核开放的 SDK 与扩展面实现。原因是修改源码后无法跟随上游更新。当前状态下，升级内核只需修改版本号并运行全量测试。

该约束已经过一次验证：内核整体替换时，前端测试结果如下。

| 项 | 结果 |
|---|---|
| 前端测试 | 38 项 |
| 内核整体替换后 | 零改动全部通过 |
| 依据 | 前后端之间只有一份事件协议作为契约，内核差异由一个文件吸收 |

### 机制归内核，策略归应用

审批分级、上下文瘦身、跨会话记忆属于应用层；工具如何执行属于内核。两者分工明确。

内置能力与第三方插件走**同一条注入管线**，不存在特权路径。新增工具只需在插件目录放入一个文件；接入新的模型服务只需在 GUI 中新建档案，不需要修改业务代码。

![插件面板：内核注册的 11 个能力域插件，开关只对新建会话生效](plugin-panel.webp)
_插件面板：内核已注册 11 个能力域插件，开关只对新建会话生效，第三方插件走同一个 PluginHost_

### 失败时默认拒绝

所有审批路径均为 fail-closed：

| 情况 | 处理 |
|---|---|
| 审批通道未建立 | 拒绝 |
| 120 秒内无决议 | 自动拒绝 |
| 回合收尾时仍未批准 | 统一拒绝 |

![ask_user 批量抉择卡片：多个问题合并，确认后一并提交](ask-user-batch.webp)
_审批走 ask_user：多个问题合并成一次抉择，选完再一并提交_

### 没有数据的优化，不算优化

优化的前提是前后对照数据。

### 测试不全绿，不算做完

测试尽量不产生费用：开发、联调与集成测试使用本地假模型服务，回归测试成本为零。

## 四、同一套内核，同时提供 Web、GUI、TUI

桌面端（GUI）、浏览器（Web）、终端（TUI）三种界面共用同一个本地服务与同一份会话。

### 三种界面

同一个服务运行在本机，三种界面接入：

| 界面 | 实现 |
|---|---|
| 桌面端（GUI） | Tauri 无边框窗口，含会话管理与数据面板，以及独立的桌宠小窗 |
| 浏览器（Web） | 访问同一个本机端口 |
| 终端（TUI） | 键盘操作，读取同一份配置 |

### 会话与配置共用

**在终端中进行的会话，在桌面端侧边栏可见并可继续；反向同样成立。** 在 GUI 中更换的模型，在终端中继续生效。

## 五、桌宠

### 名称

桌宠名为**丢丢**，来自一只真狗的名字。

### 状态映射

桌宠的作用是显示 Agent 的当前状态：

| Agent 状态 | 桌宠表现 |
|---|---|
| 等待输入 | 待命 |
| 模型思考 | 趴下歪头 |
| 工具执行 | 小碎步 |
| 等待审批 | 坐直盯视 |
| 出错 | 委屈表情（状态粘性，不会一闪而过） |
| 任务完成 | 摇尾巴 |

![桌宠预览：思考中的丢丢，以及六种状态切换](doudou-preview.webp)
_桌宠预览：待命中／思考中／执行工具／等你批准／出错了／搞定啦_

### 实现

- CSS 精灵表驱动动画，`steps()` 的采样点取值写在注释中（`jump-end` 会错位半帧）；
- 系统开启“减少动态效果”时降低播放速度，不直接停止；
- 图片加载失败时降级为单帧。

资产管线方面：早期 AI 生成的精灵图出现整批网格错排，根因是使用生成器自身校验的循环验证。此后资产管线增加了确定性质检与一道 ASCII 目检门禁。

## 六、皮肤系统

界面提供两套视觉：**像素风**与**现代风**。

| 皮肤 | 构成 |
|---|---|
| 像素风 | 切角窗口、阶梯阴影、点阵标题、8×8 网格图标 |
| 现代风 | 圆角、细描边、24×24 线性图标 |

![像素风与现代风并排对比：同一套组件，两种观感](cover.webp)
_两套皮肤并排：左像素风、右现代风，组件样式一行都不重复_

### 实现方式

术语使用“皮肤”而非“人格”：代码中没有第二个 persona，两套皮肤是同一套功能的两种观感。

实现上没有维护两套样式表。现代风是一层**观感原语覆盖**（圆角、阴影、字体栈），组件样式不重复。38 个通用图标各自定义像素网格与 SVG 描边两套画法，品牌图标同理。切换即时生效。

### 皮肤包

皮肤以外挂包形式提供：**一个目录 + 一个 skin.json**，分三级——仅更换配色、更换造型、整体重做界面。

![外观设置：皮肤从目录安装、界面主题、界面风格、背景与桌宠表现](appearance-settings.webp)
_外观设置：皮肤可从目录安装，主题／风格／背景／桌宠表现都在这一屏_

### 皮肤包不允许包含可执行代码

皮肤包中禁止出现可执行代码：

```text
js / script / eval / entry / import / require ...
```

出现这些字段会被明确拒绝，而不是忽略。原因有两点：皮肤包可以安全分享（安装一个包不等同于安装一段来源不明的程序）；卸载可以保证干净（没有 JS 即没有作者自定义的副作用，运行时对界面的全部操作可枚举）。

多数插件系统的风险来自这一点：为追求灵活放弃限制，最终用户不敢安装第三方包。

## 七、当前状态与后续计划

RoughAgent 当前可用，但仍有明确的未完成项。

### 名称

名称来自工作室名 RoughStone，含义是不预设结果。

### 未完成项

代码注释中的设计说明与已声明的边界（例如三种界面目前只有配置与内容同源，工具面尚未完全对齐）标记的是未完成项，不代表已完成状态。

### 后续目标

后续目标是成为自研引擎 RoughEngine 的专属开发 Agent；已预留引擎扩展面与终端界面。

在此之前，它作为个人 Agent 运行在本机：数据保存在本地，服务只监听本机，功能按需扩展，并给出每一轮的实际花费。

---

## 小结

本文的起点是成本不透明。现在的状态是：每次请求的花费、缓存命中、工具耗时与耗时来源，都在界面上可查。

设计目标是让花费与能力边界可验证：花了多少钱、能做到什么、做不到什么，都有对应数据。未完成项已在上节列出。
