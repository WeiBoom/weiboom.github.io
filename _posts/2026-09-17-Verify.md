前面几篇讲钱、讲上下文、讲内核。这一篇讲一个问题：**我怎么知道它还是对的。**

今天这个仓库里有 **151 个测试文件**（后端 91 + 前端 60），外加一套 eval 任务集。数字本身没什么可吹的，值得说的是它们的分工：

> **测试守住「不能坏」，评测判断「有没有变好」。**

这是两件事。只有前者，你会陷在原地打磨；只有后者，你会在某次重构里悄悄弄坏一个老功能。

## 一、三层防线，各回答一个不同的问题

![三层防线，各自回答一个不同的问题](three-layers.webp)
_单元测试问「零件对不对」，集成测试问「循环闭得住吗」，eval 问「这个 Agent 好不好」_

- **单元测试**：翻译表、审批策略、预算算法、PNG 编解码……全部 mock，**零成本**。它管的是“零件”。
- **集成测试**：把 Pi 循环 + 翻译层 + 审批 + 断言这整条护栏串起来跑一遍，mock 全链路。**升级内核版本之后必跑**——这一层就是上一篇说的“内核与应用之间那条线”的守卫。
- **eval**：任务成功率、平均步数、平均 token、失败模式分类。它管的是“整体行为”，需要真实模型。

贯穿三层的一条纪律，我觉得比数字更重要：**断言只依赖确定性终态**——文件内容、事件序列、工具调用集合——**不匹配具体文案**。这是防 flaky 的第一条，也是最容易被违反的一条：模型换一句话说法，测试就红了，然后你就学会了“反正这个测试总红”。

### 为什么敢全 mock

### 为什么敢全 mock

因为有一个**本地假模型服务**：它按用户输入匹配剧本（`write` / `read` / 默认三种），带一个状态机——新回合重选剧本，逐步推进到完成，工具调用 ID 延续计数。

没有它，“每次改完都跑全量测试”这句话是不可能做到的：按真模型的钱跑一遍回归，没人会天天跑。有了它，回归是**零成本**的，而且它测的是**我们自己那层**（翻译、审批、上下文治理、落盘）——模型升级换代时，这一层本来就不该变。

## 二、门禁要能拦住「悄悄变差」

![门禁要能拦住「悄悄变差」](verdict-gate.webp)
_回归是确定的事实，劣化是度量 —— 两者在门禁里的地位不该一样_

这里有个我自己踩过的坑。最初的 runner **只判断「本次有没有任务失败」**。它能拦住“变红”，但拦不住这些：

```text
本来 2 步做完的任务，变成 5 步
token 从 7.5k 涨到 20k
成功率仍然 6/6 —— 门禁一路放行
```

而“变慢变贵”恰恰是这类项目最在意的那种退化。于是加了**基线**：同一个任务，上次过、这次挂 = **回归**；都过但指标涨过阈值 = **劣化**。

### 一条我犹豫过的取舍

接下来是一条我犹豫过、但最后很确定的取舍：

- **mock 模式**：剧本写死，token 和步数是**确定值**。此时指标涨了就是真的涨了，**可以阻塞合入**；
- **真实模型模式**：同一个任务跑两次，token 差一两成是常态（采样、缓存命中、供应商侧波动）。拿它当硬门禁，结果会是一个**时红时绿的 CI**。

> 一个会随机变红的门禁，等于没有门禁——人们会学会无视它，然后连真回归也一起无视。

所以现在的规则是：**回归在两种模式下都阻塞**（它是确定的事实，不是度量）；**指标劣化只在确定值模式下阻塞**，真实模型模式只报告。

## 三、eval 长什么样

任务集按维度分组：单步、多步、自我纠正、变体、检索、纪律、精度。每个任务带三样东西：独立工作区、可选的工作区预置、以及一个**机器断言**（抛错就算失败）。

指标除了成功率，还有平均步数、平均 token，以及**失败模式分类**：

```text
turn-error      回合异常（LLM / 网络错误，不是模型能力问题）
assert-failed   终态断言失败（模型没把任务做对）
no-tool-call    完全没调工具就结束（模型没理解任务）
```

### 失败分类比成功率有用

**失败分类比成功率有用。** 三种失败的修复动作完全不同：第一种该去看供应商状态，第二种该改 prompt 或工具描述，第三种该改任务本身的表述。只有一个成功率，你只知道“又挂了”。

最近一次 mock 报告：6 个任务全过，平均 2.33 步、8.8k token、111 毫秒。**但请把这组数字读成「护栏本身是通的」，而不是「这个 Agent 很强」**——mock 模式下模型是假的，它证明的是“我们的循环和翻译层没问题”。

所以 eval 是双模式的：mock 模式零 token，用来验证护栏；真实模型模式跑全量，用来当发布判据。

## 四、最容易做坏的地方：断言本身

有一组测试的名字我很喜欢，叫 `computed-then-dropped`（算出来又丢掉）。它的文件头写着：

> 共同形态是：**值已经算出来了，但没有任何出口**。这类问题不会让任何测试变红——算得对、也没人要，于是永远不会被发现。

里面钉了三处：

1. **重试原因是编的。** 内核把原话给了我们（`429 Too Many Requests`、`401`、DNS 不通），我们却统一显示“服务商暂时不可用”。用户看到这句话会去**等**、去**重试**，而不是去换密钥或改配置。
2. **子代理的上限只活在代码里。** 界面文案里手抄了一份数字，常量改了文案不改——界面会长期显示一个已经不成立的数字，而两边各自都是“对的”。
3. **插件切换的生效时机说明前端不显示**（开关只对新会话生效，这件事必须说出来）。

### 一个守不住的断言长什么样

第 3 条还留了一个更狠的教训。它起初写的是一条**源码扫描**：断言某个组件源码里出现过那个字段名。我做了个反向对照——把 `if (d.note)` 改成 `if (false && d.note)`，**扫描照样全绿**。

> 那种「看着在守、其实守不住」的断言，比没有断言更糟。

后来改成了前端行为测试：渲染 → 点开关 → 断言那句话真的出现在 DOM 里。

## 五、我给测试定的五条纪律

1. **断言只依赖确定性终态**，不匹配具体文案；
2. **涉及数字的文案必须由常量生成**，并且单测拿常量去比——手抄的数字一定会漂移；
3. **会随机变红的门禁必须降级为“只报告”**，否则连真回归也会被无视；
4. **涉及外部事实的缺省值**（内核默认值、单价表）**必须与来源逐字一致**，并让单测直接调来源把它钉死。内核升级改了那张表而我们没跟，界面显示的“生效值”就是错的——而且两边各自都觉得自己对；
5. **源码扫描只能当辅助，行为测试才是门禁。**

石头还在磨。至少现在，“它坏了吗”和“它更好了吗”是两个能分别回答的问题。
